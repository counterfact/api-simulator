# Lesson workflows, approvals, and history

- In build-up tutorials, start at the real generated scaffold and keep tutorial infrastructure separate from learner-authored behavior. Validate incomplete states as well as the final implementation; saved-file probes must use isolated state, and preview navigation must never apply prerequisite code or seed live state implicitly. When a tutorial prepares code, show its exact diff before writing, require an explicit apply action, update the proposal with the applied result, and reject stale previews if the learner saves in the meantime. Share the transformation between preview and apply, preserve learner edits, and leave the central behavior as a focused exercise. Conversational guides must retain proposals, approval replies, results, and quiz feedback in chronological order across reloads; reveal follow-up exercises only after their supporting edits succeed. Record explicit UI actions separately from automatic follow-up requests, and describe HTTP outcomes only from actual responses. Attach immutable request/response snapshots to the initiating action with a handler link and collapsed details; retain failed or interrupted exchanges without inventing a response. Keep HTTP statuses, API diagnostics, and inspection instructions in the conversation; the storefront uses ordinary customer-facing confirmations, errors, and empty states. Keep file-change attribution separate from lesson completion. Capture the generated baseline first, distinguish approved tutor writes from learner saves, and retain both sides of each diff without collecting unrelated project files or sending source text through telemetry. Version lesson protocols when changing progression and retain helper compatibility for already generated projects. If inserting lessons changes numeric checkpoints, keep the prior phase inventory for existing journals and telemetry callers rather than interpreting their progress with the new numbering.
- Keep the current tutorial script, learner instructions, Milo actions, and completion predicates together in executable lesson graphs. The browser should report observations and present graph results rather than duplicate phase-specific completion rules. Generate workflow diagrams from those graphs, and preserve historical protocol inventories separately when refactoring current lessons.
- Keep tutorial LangGraph invocations bounded to one learner event, with explicit wait states at approval and lesson boundaries. Read durable progress from the project journal on each invocation; do not add an in-memory checkpoint store that can disagree after restart. Keep graph decisions on the server and presentation pacing in the browser. Test that preview and polling cannot write files or advance lessons, and that concurrent events do not share request state.
- Separate durable tutorial lesson checkpoints from runtime observations. Validate saved implementations independently of exploratory live data. Live reset completion must match the full relevant catalog and inventory baseline rather than one scalar. Hints for mutable setup must inspect existing state, guide correction of duplicate or partial data, and avoid repeating append operations. Refresh open hints after validation and state changes without silently modifying learner data. Returning projects must resume without reverting evolved handlers; cart, quiz, and HTTP observations need a fresh session. Validate incomplete implementations with inputs that distinguish the provided stub from the intended behavior, and keep feedback attached to the method that failed. Preserve disclosure choices when rerendering a persistent transcript.
- Guided exercises describe the edit location, intended behavior, and observable result without supplying learner solution snippets or prepared REPL commands. Name a focused change directly when useful, such as replacing `.random()` with `.json(catalog)`, while leaving the learner to implement it. Keep learner solutions out of serialized lesson metadata; proposed tutor changes and already saved learner work remain visible as diffs. Exercise instructions and successful-save feedback must name the next concrete action, including prerequisites such as adding an item before checkout, the actual control label, and the expected result. Give follow-up guidance when a multi-action experiment is only partly complete. Break long explanations into smaller messages with an Okay button to reveal the next part. Reveal at most one new tutor bubble per user action, and pause between the final part of an explanation and the next message as well as between short consecutive messages. Background checks and reloads must not advance this pacing. Track actually displayed bubble identities independently of section acknowledgments, so restored counts cannot reveal several unseen bubbles in one render. Distinguish reading pauses from action prompts: Okay only reveals explanatory text, while action prompts wait for actual approvals, saved edits, REPL submissions, or API experiments. End each action prompt at the instruction: put necessary context and expected results before it, and reveal the next task only after the requested work. Editing prompts stop at saving; successful-save feedback introduces the API or REPL experiment. Do not append metadata instructions, cleanup steps, quiz questions, or later experiments after an action. Stage multi-step experiments from observed saves, refreshes, responses, and progress checks. Detect progress automatically from verified saves and observable running state; never require a manual check button. Offer a Hint button at every learner-action prompt, with precise, stage-specific instructions. Hints must not apply edits, submit commands, send API requests, answer quizzes, acknowledge queued messages, or earn progress. Preserve requested hints in the conversation across reloads. Combine short explanations with their instructions instead of inserting reading acknowledgments before required work. Completed lessons are history, not new work to acknowledge again. Animate only new text, preserve inline links and code during typing, and respect reduced-motion preferences for typing and scrolling. Preserve revealed messages across reloads; acknowledgment only reveals text and must not apply edits, run scenarios, or credit lesson completion.

Begin the current guided flow with a coffee order before code inspection. Source-only phases may complete from isolated saved-code checks; purchase and REPL experiments require their own observed results.

When the generator's public type structure changes, align prepared lesson code
with the [route guidance](../../route/SKILL.md) and compile the completed exercises
against a freshly generated project. Preserve existing handler annotations and
learner edits when resuming older demos; do not migrate them implicitly during
preparation. Keep historical fixtures explicit about the compatibility they test.
